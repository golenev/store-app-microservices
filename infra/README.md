# Как приложение получает базы данных при запуске через Docker

В `infra` хранится один скрипт: [postgres/init/01-databases.sql](postgres/init/01-databases.sql). Он подготавливает PostgreSQL для трёх приложений: создаёт каждому свою базу, пользователя и права подключения. Скрипт нужен при первом запуске нашего Docker Compose на пустом хранилище данных.

Без этой подготовки новый PostgreSQL запустится, но приложения не смогут подключиться: они ожидают базы `store_db`, `tariffs_db`, `warehouse_db` и соответствующих пользователей. Сам файл не является обязательным для PostgreSQL. Его можно заменить ручной подготовкой или другим средством настройки. В текущем проекте эту работу выполняет именно он.

## Что здесь означает «локальная инфраструктура»

Приложению нужны отдельные программы, с которыми оно обменивается данными. PostgreSQL хранит данные, Kafka передаёт события между сервисами, Redis хранит кеш тарифов. [docker-compose.yml](../docker-compose.yml) запускает эти программы в контейнерах — отдельных процессах с подготовленным окружением.

«Локальная» означает, что окружение запускается на машине разработчика через Docker. Та же конфигурация используется в CI — автоматических проверках pull request. Каталог `infra` сейчас содержит только подготовку PostgreSQL. Kafka и Redis настраиваются непосредственно в Compose; этот SQL их не создаёт и не запускает.

## Кто запускает SQL и в какой момент

Разработчик выполняет из корня проекта:

```powershell
docker compose up -d --wait postgres kafka redis
```

Эта команда запускает зависимости. Сами Java-приложения после этого можно запустить из IDEA. При полном запуске `docker compose up -d --build --wait` Compose также собирает и запускает приложения.

При первом запуске PostgreSQL происходит следующая последовательность:

1. Compose запускает контейнер из образа `postgres:16-alpine`. Образ содержит PostgreSQL и программу первоначальной настройки.
2. Compose подключает постоянное хранилище `postgres-data` к `/var/lib/postgresql/data`. Такое хранилище называется Docker volume: данные в нём переживают удаление и создание контейнера.
3. Compose делает каталог `infra/postgres/init` доступным внутри контейнера под именем `/docker-entrypoint-initdb.d`. Суффикс `:ro` в настройке разрешает контейнеру читать файлы, но запрещает менять исходники в этом каталоге.
4. Программа первоначальной настройки обнаруживает отсутствие созданной базы PostgreSQL в хранилище. Она создаёт начальные файлы данных, администратора `bootstrap_admin` и базу `bootstrap_db`, указанные в переменных `POSTGRES_USER` и `POSTGRES_DB`.
5. Затем эта программа читает SQL-файлы из `/docker-entrypoint-initdb.d`. Наш `01-databases.sql` выполняется через `psql` — средство отправки SQL-команд серверу PostgreSQL — от имени `bootstrap_admin`.
6. После подготовки PostgreSQL запускается в обычном режиме. Приложения подключаются к собственным базам; Flyway внутри каждого приложения создаёт таблицы и начальные данные.

Автоматическое выполнение файлов — поведение официального образа PostgreSQL, а не специальный Java-код проекта. Его условия и вызов `psql` видны в [исходнике программы запуска образа](https://github.com/docker-library/postgres/blob/master/docker-entrypoint.sh).

## Что именно создают команды скрипта

Внутри одного контейнера PostgreSQL создаются три отдельные базы. Для каждой есть свой пользователь. В PostgreSQL пользователь с правом входа называется ролью с `LOGIN`.

| Приложение | Создаваемая база | Пользователь приложения |
| --- | --- | --- |
| STORE | `store_db` | `store_app` |
| TARIFFS | `tariffs_db` | `tariffs_app` |
| WAREHOUSE | `warehouse_db` | `warehouse_app` |

Это разделение позволяет каждому сервису подключаться к собственной базе со своими правами. Контейнер PostgreSQL общий, поэтому разделение баз не означает три независимых сервера.

Например, первые команды для STORE имеют такой смысл:

```sql
CREATE ROLE store_app LOGIN PASSWORD 'store_local' NOSUPERUSER NOCREATEDB NOCREATEROLE;
CREATE DATABASE store_db OWNER store_app;
```

Первая команда создаёт пользователя, задаёт пароль и запрещает ему полномочия администратора, создание новых баз и ролей. Вторая создаёт базу `store_db` и назначает этого пользователя её владельцем. Он сможет создавать таблицы в своей базе, поэтому миграциям приложения не требуется подключение под администратором.

Далее скрипт настраивает подключения:

```sql
REVOKE CONNECT ON DATABASE store_db FROM PUBLIC;
GRANT CONNECT ON DATABASE store_db TO store_app;
```

`PUBLIC` означает общее право для всех ролей. `REVOKE` убирает такое право подключения, а `GRANT` выдаёт его конкретному пользователю. Аналогичные команды выполняются для TARIFFS и WAREHOUSE. Поэтому пользователь STORE не получает доступ к базе TARIFFS только за счёт общих разрешений.

Скрипт также убирает общее право подключения к `bootstrap_db`, `postgres` и `template1`. Администратор `bootstrap_admin` сохраняет свои полномочия; приложения используют ограниченные сервисные роли. Пароли в этом файле согласованы с Compose и локальными настройками приложений и предназначены для учебного окружения.

## Почему Flyway не заменяет этот скрипт

SQL из `infra` подготавливает базы и пользователей. Flyway создаёт таблицы **в уже существующей базе**, применяя файлы из `src/main/resources/db/migration` соответствующего сервиса.

Для STORE порядок такой: сначала появилась база `store_db` и пользователь `store_app`; затем приложение подключилось к ней; после этого Flyway создал таблицы остатков, корзин и заявок. Подключение невозможно, если нет базы или подходящего пользователя. До применения миграций в таком случае дело не дойдёт. Кроме того, сервисная роль имеет `NOCREATEDB` и сама новую базу создать не может.

В настройках приложений `spring.sql.init.mode` равен `never`: Spring не выполняет отдельный SQL первоначальной настройки. Подготовку баз выполняет образ PostgreSQL, а подготовку таблиц — Flyway.

## Где это используется и какие тесты от этого зависят

| Запуск или проверка | Использует SQL из `infra`? | Как получает базу |
| --- | --- | --- |
| Приложения из IDEA со штатными локальными настройками | Да, при первой подготовке их Compose-окружения | Подключаются к сервисным базам через порт `34567` |
| Полный запуск приложений через Compose | Да, при первой подготовке хранилища | Подключаются к контейнеру `postgres` через порт `5432` |
| Unit-тесты чистой логики и тесты с Mockito | Нет | Работают без PostgreSQL |
| Контрактные тесты | Нет | Проверяют JSON и схемы без базы |
| Java-проверки с PostgreSQL Testcontainers | Нет | Testcontainers создаёт отдельный контейнер и тестовую базу; тестовый код применяет миграции |
| Kotlin API-проверки и Selenide на штатном окружении | Косвенно | Вызывают запущенные приложения; некоторые также читают их базы через Exposed |
| CI: задания `e2e` и `compose-smoke` | Да, при первой подготовке хранилища | Запускают тот же Compose перед проверками |

SQL из `infra` обеспечивает окружение приложений. Он не является общей подготовкой данных для всех тестов. Если Kotlin-набор направлен на другое окружение, его базы должны быть подготовлены там; локальный файл сам по себе на удалённом сервере ничего не выполнит.

## Что произойдёт, если убрать файл

**На новом пустом хранилище:** образ PostgreSQL создаст администратора и начальную базу из переменных Compose, но три сервисные базы и пользователя не появятся. При запуске STORE запросит подключение к `store_db` под `store_app` и получит ошибку подключения. Аналогично не смогут подключиться остальные приложения. Точная ошибка зависит от того, отсутствует пользователь, база или оба объекта.

При этом проверка готовности самого PostgreSQL может пройти: наш `pg_isready` обращается к `bootstrap_db` под `bootstrap_admin`. Доступность PostgreSQL не доказывает, что базы приложений подготовлены. Проверки приложений в полном Compose и последующие API/UI-сценарии не смогут успешно завершиться.

**На уже подготовленном хранилище:** базы и пользователи остаются в volume. Удаление SQL не удалит их, поэтому текущий запуск может продолжить работать. Но запуск на новой машине или на CI с пустым хранилищем сломается. Именно поэтому работоспособность старого контейнера не позволяет признать файл неиспользуемым.

Отказаться от файла можно, если другим способом заранее создать те же базы, пользователей и права либо изменить настройки приложений под другое подготовленное окружение. Например, эти действия может выполнять администратор PostgreSQL. Тогда новая процедура должна применяться и на машине разработчика, и в CI. Простое удаление файла такой процедуры не создаёт.

## Что меняется при повторном запуске

Образ определяет наличие подготовленного хранилища по файлу `PG_VERSION`. Если оно уже подготовлено, файлы из `/docker-entrypoint-initdb.d` повторно не выполняются. Обычный перезапуск и пересоздание контейнера с прежним volume сохраняют базы и данные. Изменение `01-databases.sql` не обновит существующих пользователей и права.

Сам SQL не рассчитан на повторное выполнение целиком: `CREATE ROLE` и `CREATE DATABASE` завершатся ошибкой, если объекты уже существуют. Если первый запуск оборвался посередине, часть объектов могла сохраниться. Перезапуск не гарантирует продолжения подготовки; нужно проверить состояние и выполнить только недостающие действия. Изменения существующего окружения требуют отдельной процедуры, а не удаления volume ради запуска файла ещё раз.

## Как проверить подготовку без изменения данных

Следующие команды выполняются из корня репозитория. Они читают список баз и пользователей уже запущенного PostgreSQL:

```powershell
docker compose exec -T postgres psql -U bootstrap_admin -d bootstrap_db -c "SELECT datname, pg_get_userbyid(datdba) AS owner FROM pg_database WHERE datname IN ('store_db', 'tariffs_db', 'warehouse_db') ORDER BY datname;"
docker compose exec -T postgres psql -U bootstrap_admin -d bootstrap_db -c "SELECT rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole FROM pg_roles WHERE rolname IN ('store_app', 'tariffs_app', 'warehouse_app') ORDER BY rolname;"
```

Первый запрос должен показать три сервисные базы с соответствующими владельцами. Второй — три роли с разрешённым входом и без полномочий администратора, создания баз и ролей. Эти запросы проверяют подготовку объектов, но не таблицы, бизнес-данные или все права доступа. Применение миграций и работу приложений проверяют следующие уровни запуска и тестов.

10 октября 2026 обе команды выполнены на работающем `shop-runtime`: найдены три указанные базы с соответствующими владельцами и три роли с `LOGIN` без перечисленных административных полномочий. Данные не изменялись. Это проверка текущего состояния; отдельный первый запуск на пустом хранилище в рамках документации не воспроизводился.

Основания описания: [настройки Compose](../docker-compose.yml), [SQL подготовки](postgres/init/01-databases.sql), настройки `application.yaml` трёх сервисов, Java-конфигурации PostgreSQL Testcontainers, Kotlin `DbFactory` и [задания CI](../.github/workflows/product-flow-test.yml). Это описание существующего устройства; новый прогон приложений и тестов для его подготовки не выполнялся.
