# Правила реализации

## Согласованный объём

Целевая архитектура и последовательность задач описаны в `docs/implementation-plan.md`. Ключевые сквозные сценарии находятся в `CASES.md`. Перед выполнением задачи прочитать эти документы и текущий README. Технический паспорт и первоначальное ревью отражают более ранний вариант; согласованные изменения в плане имеют приоритет.

Backend остаётся на Java 21. Kotlin используется в E2E. Существующий HTML адаптируется под новые API. Исторические данные не мигрируются: новая версия использует чистые базы и воспроизводимые fixtures. Не удалять существующие базы, Docker volumes или файлы без явного запроса пользователя.

## Документация функций

Над каждой написанной или изменённой функцией/методом, включая private helpers, тесты, явно объявленные конструкторы и JavaScript-функции, писать документацию. Java — Javadoc, Kotlin — KDoc, JavaScript — JSDoc. При изменении существующего файла документировать также оставшиеся явно объявленные функции этого файла, чтобы переданный следующей LLM модуль был понятен целиком.

Описывать назначение, входы и результат. Для нетривиальных операций дополнительно описывать побочные эффекты, границу транзакции, повторный вызов, блокировки и значимые ошибки. Для тестов — исходное состояние, действие и проверяемый инвариант. Комментарий должен объяснять контракт, а не пересказывать имя функции. Обновлять документацию вместе с поведением. Методы, автоматически генерируемые Lombok, не имеют отдельного тела в исходниках; документировать соответствующие поля и класс.

## Работа по задачам

- Одна задача — одна ветка `codex/<task-name>` и один PR с её реализацией, тестами и документацией.
- Сначала завершить зависимые задачи и включить их в базовую ветку. Последовательные задачи начинать от актуальной `master`, а не от незавершённой feature-ветки. Перед началом проверить состояние репозитория и remote default branch.
- Не переносить чужие незакоммиченные изменения в свои коммиты. При необходимости использовать отдельный worktree.
- В каждом PR обновлять README и релевантные сценарии CASES: фактическое состояние, команды, ограничения и проверки.
- Не заявлять работу будущих компонентов как уже реализованную.
- У каждой задачи есть собственные осмысленные проверки; финальная E2E-задача не заменяет тесты предыдущих задач.
- PR должен содержать проблему, итоговое поведение, выполненные проверки и существенные ограничения. Не включать нерелевантный рефакторинг.
- Не публиковать фиктивные PR для пустых веток. Создавать PR после реализации и проверок соответствующей задачи.

## Инварианты

STORE хранит одну позицию остатка на `(storeId, productId)`. Новая уникальная поставка увеличивает количество. Цена всего доступного остатка определяется последней успешно оприходованной поставкой по её неизменяемому порядку первой приёмки в WAREHOUSE; поздний повтор старой поставки не откатывает цену.

Корзины независимы и ничего не резервируют. Добавление проверяет текущий остаток и итоговое количество позиции в своей корзине. Оформление проверяет остатки снова. Списание, движения, submission, outbox и закрытие корзины выполняются атомарно.

Idempotency-Key уникален внутри магазина. Повтор принятого запроса возвращает ту же операцию без нового расхода. Повтор Kafka-события не создаёт повторный приход. Outbox допускает повторную физическую публикацию с тем же идентификатором.

Ожидающие pricing поставки восстанавливаются автоматически, в том числе после перезапуска. Фоновые попытки и ручной диагностический retry не должны создавать два оприходования.

## Тесты

Предпочитать явные независимые сценарии и данные (DAMP). Не создавать универсальный тестовый движок с множеством флагов. Проверять асинхронный результат ограниченным ожиданием состояния. Сбои и задержки воспроизводить управляемыми точками только в тестовом профиле. Не помещать произвольный sleep в обычную бизнес-логику.

Изолировать storeId, cartId, deliveryId и ключи операций между параллельными тестами. Проверки глобального сброса тарифного кеша изолировать от других тестов кеша. Успех unit-тестов не объявлять успехом интеграционных или E2E-проверок.
