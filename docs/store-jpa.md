# Spring Data JPA на примере STORE

STORE выбран из-за атомарного оформления: корзина, JOIN позиций с остатками, блокировки, расходные движения, идемпотентность и outbox. Это пример работы ORM поверх существующего контракта PostgreSQL, а не новая схема магазина.

## Сущность и таблица

`@Entity` отображает таблицу, `@Id` задаёт идентификатор, `@Column` — колонку. Деньги остаются `BigDecimal` с точностью 28 и масштабом 2. Даты — `Instant`, колонки PostgreSQL — TIMESTAMPTZ. Составные ключи описаны отдельными `@IdClass`; равенство ключа использует все его части.

В STORE 11 сущностей для действующих таблиц и 5 классов составных ключей. Исторические `product`, `cart` и `orders` не обслуживаются новой моделью и не отображаются в сущности. Миграции V1–V3 не изменены.

Lombok генерирует доступ к полям, конструкторы и builder. У сущностей нет `@Data`, равенства по всем изменяемым полям или автоматического обхода связей. У `CartItemEntity.stock` есть `@ManyToOne(fetch = LAZY)` без каскадов; связь используется для чтения, её UUID записывается через `stockItemId`. Поэтому изменение позиции корзины не сохраняет и не удаляет остаток каскадом.

Flyway остаётся владельцем схемы. `spring.jpa.hibernate.ddl-auto=validate` проверяет соответствие таблиц отображению, но не заменяет проверки CHECK, UNIQUE и внешних ключей. `open-in-view=false` закрывает контекст после транзакции. Контроллеры возвращают DTO, а не сущности или ленивые коллекции.

## Что делает JpaRepository

`InventoryJpaRepository` наследует `JpaRepository<InventoryEntity, UUID>`. Например, `findByStoreIdOrderByProductId` получает SQL из имени метода и применяет ограничение `Pageable`; `countByStoreId` считает строки без загрузки остатков.

Для JOIN используется явный JPQL: `CartItemJpaRepository.lines` выбирает поля корзины и остатка сразу в `CheckoutLine`. ORM создаёт один SQL-запрос. Сервис не обходит ленивую связь для каждой строки; значит, число запросов не растёт вместе с числом позиций.

`SubmissionJpaRepository.views` тоже возвращает DTO-проекцию, соединяя принятие и состояние публикации. В сервисах больше нет `Map<String,Object>` и кастов по строковым именам колонок.

## Dirty checking вместо ручного UPDATE

Репозиторий находит управляемую сущность в открытой транзакции. После `entity.setAvailableQuantity(...)` Hibernate запоминает изменение и отправляет UPDATE при `flush` или commit. Для уже управляемого объекта дополнительный `save` не нужен.

Так меняются остаток, цена, версия корзины и токен outbox. К моменту построения ответа JPQL-запрос автоматически сбрасывает ожидающие изменения. Сервис возвращает обновлённый DTO в той же транзакции.

Версия корзины остаётся явной версией API под пессимистической блокировкой. Она не помечена `@Version`: автоматическое увеличение Hibernate поменяло бы существующие правила `expectedCartVersion`, повторов и исчерпания версии.

## save, persist и flush

`save` удобен для изменения позиции корзины: под блокировкой корзины выбирается существующая позиция или создаётся новая. В тестах `saveAndFlush` подготавливает обычные сущности и проверяет ограничения до завершения подготовки.

У новой сущности с уже назначенным UUID и без `@Version` Spring Data обычно выбирает `merge`. Это отличается от строгой вставки: существующий идентификатор может привести к обновлению записи. Поэтому новые корзины, принятые поставки, заявки, движения и outbox сохраняются через `EntityManager.persist`.

Явный `flush` гарантирует порядок вставок для скалярных внешних ключей и выявляет нарушения UNIQUE внутри операции репозитория. Это отправка SQL, а не commit: все изменения всё ещё можно откатить. Плата за сохранение текущей схемы и точного порядка — дополнительные flush; пакетные вставки здесь не оптимизировались.

## Блокировки и оформление

`SubmissionTransactionService.accept` сохраняет `REQUIRES_NEW`:

1. Проверяет прежний Idempotency-Key.
2. Блокирует корзину через `@Lock(PESSIMISTIC_WRITE)`.
3. Проверяет состояние и версию, блокирует остатки в порядке UUID.
4. Повторно проверяет ключ после ожидания блокировок и проверяет весь состав.
5. В одной транзакции сохраняет submission, уменьшает остатки, записывает расходы и outbox, закрывает корзину.
6. Возвращает принятую заявку после успешного завершения операции.

Порядок UUID сохранён в PostgreSQL-запросе, чтобы два оформления брали пересекающиеся остатки в одном порядке. Корзины ничего не резервируют до оформления.

Если две транзакции дошли до одного UNIQUE ключа, Hibernate/Spring выдаёт `DataIntegrityViolationException`. `SubmissionService` распознаёт только SQLSTATE `23505`, ждёт отката проигравшей операции и читает победителя в новой транзакции. CHECK, NOT NULL и внешние ключи не маскируются повтором. Совпавший запрос получает прежнюю заявку, другой — `IDEMPOTENCY_KEY_REUSED`.

## Где остаётся native SQL

| Запрос | Причина |
| --- | --- |
| `pg_advisory_xact_lock` для eventId | Блокирует также идентификатор, для которого ещё нет строки; обычный `@Lock` этого не делает |
| JOIN оформления с `FOR UPDATE OF i` | Блокирует именно остатки, сохраняя прежний порядок UUID и набор блокируемых таблиц |
| Outbox `FOR UPDATE SKIP LOCKED` | Пропускает запись другого работника без ожидания; точная PostgreSQL-семантика видна в коде |
| Диагностика `ON CONFLICT DO NOTHING` | Атомарно дедуплицирует координаты Kafka, не превращая конфликт в откат всей обработки |

Native-запросы выполняются через JPA и используют ту же транзакцию и соединение. Остальное хранение использует сущности, Spring Data и JPQL; `JdbcTemplate` в STORE больше нет.

Подтверждение/повтор отправки — JPQL bulk UPDATE с проверкой `leaseToken`. У этих методов `@Modifying(flushAutomatically=true, clearAutomatically=true)`: ожидающие изменения сохраняются перед UPDATE, а устаревшие сущности удаляются из контекста после него. Отправка Kafka остаётся вне SQL-транзакции.

## Проверки

Тестовый контекст использует PostgreSQL Testcontainers, настоящие Flyway, Hibernate `validate`, `JpaTransactionManager` и Spring Data-репозитории. Преобразование исключений и строковая запись дат соответствуют Spring Boot. Подготовка, бизнес-операция и контрольное чтение завершают отдельные транзакции; проверки не читают результат из прежнего кеша первого уровня.

14 существующих API-сценариев сохранены: создание/чтение/изменение/удаление корзины, ошибки, каталог, оформление и повтор. Подготовка данных и проверки переведены с JDBC на JPA.

11 дополнительных `STORE-JPA-001`–`011` проверяют:

- порядок приходов и повтор с прежним/новым eventId;
- первый приход нового продукта;
- дедупликацию диагностик;
- отсутствие записей после нехватки;
- откат всех записей после ошибки UNIQUE после flush/clear;
- конкуренцию корзин за последнюю единицу;
- одновременное оформление с одним ключом;
- пропуск чужой блокировки outbox;
- истечение токена и отказ старому подтверждению;
- backoff без второго списания;
- реальный конфликт INSERT по UNIQUE и чтение победителя после отката в REQUIRES_NEW.

Конкурентные сценарии используют отдельные транзакции, ограниченные latch/future и ожидание блокировки PostgreSQL. Произвольных sleep в бизнес-коде нет. Kafka в этих Java-сценариях не запускается; публикация проверяется отдельно в Kotlin E2E/CI.

```shell
mvn -pl store-service test
mvn -pl store-service -Dtest=StoreApiDatabaseTest test
mvn verify
python scripts/check-backend-layers.py
```

Нужны Java 21 и Docker. Пользовательские Compose-базы и volumes эти Java-тесты не используют.
