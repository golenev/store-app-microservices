# План изменения архитектуры

Дата согласования: 3 октября 2026 года.

Статус: задачи 1–8 включены в master через PR #37–44. Отдельная задача `codex/e2e-tech-book` переписывает существующие E2E по tech-book 1.1: Kotlin + Selenide для браузера, отчётность Allure и диагностика. Последующие замечания выполняются в codex/e2e-reference-corrections: ScenarioTemplate и отдельный профиль удалены; данные тестов сохраняются. В E2E применены Exposed, Rest Assured, отдельные файлы моделей и структура Selenide по образцу golenev-xlsx-report-system. В текущую коррекцию также входит удаление компонентов управляемых отказов из приложений и связанных runtime-проверок.

## 1. Зафиксированные решения

1. Технический паспорт — целевой контракт с изменениями, перечисленными здесь. Требования и минимальное покрытие реализуются по этапам.
2. Backend остаётся Java 21. Kotlin E2E сохраняется. Старые данные не мигрируются; новая версия получает чистые базы и fixtures. Подготовка чистой среды не является разрешением удалять существующие volumes.
3. Существующий HTML остаётся и адаптируется под новый API. Совместимость старых endpoints не требуется.
4. Авторизация, платежи, доставка, отмены, возвраты, FIFO и временные резервы исключены.
5. Магазины и города задаются fixtures WAREHOUSE. TARIFFS предоставляет CRUD правил, quote и сброс кеша.
6. Изменение существующих тарифных правил не инвалидирует заполненный кеш автоматически. Сброс вручную или ежедневно в 00:00 Europe/Moscow. Для строгого соответствия этому поведению начальная версия не использует независимый суточный TTL: он мог бы обновить значение до сброса. Явно заданная деградация при отказе Redis: расчёт по БД без кеша.
7. Корзины независимы. При добавлении проверяется итоговое количество позиции своей корзины относительно текущего остатка. Добавление не меняет остаток и не сообщает о корзине другим покупателям. При submit остаток проверяется повторно под блокировками.
8. STORE хранит одну позицию на `(storeId, productId)`. Каждая уникальная оприходованная поставка добавляет количество, а последняя поставка задаёт цену всего доступного остатка. История отдельных поставок и движений сохраняется; отдельных выбираемых партий в каталоге нет.
9. Pricing повторяется автоматически после временной ошибки и после перезапуска. Диагностический ручной retry можно сохранить, но нормальная работа от него не зависит.
10. Idempotency-Key уникален внутри магазина. HTML генерирует и сохраняет ключ до установления результата операции; сетевой повтор использует тот же ключ. Новый ключ создаётся для новой операции.
11. Поддерживаются infrastructure-only Compose + запуск приложений из IDEA и полный Compose. Unit/integration идут в CI, E2E — отдельным этапом.
12. Документация над каждой функцией обязательна. README и CASES изменяются вместе с соответствующей задачей. Правила сохранены в корневом AGENTS.md.

## 2. Изменения относительно паспорта

Паспорт описывал отдельные позиции по партиям и неизменяемую цену партии. Теперь есть единый inventory по продукту и магазину, и новая поставка меняет цену всего оставшегося продукта. Это сознательное изменение бизнес-правила.

### Пример пополнения

- Остаток 6 единиц продукта с продажной ценой 120.00.
- Приходит 10 единиц того же продукта с рассчитанной продажной ценой 144.00.
- В каталоге одна позиция: количество 16, цена 144.00.
- Повтор этой поставки оставляет количество 16 и цену 144.00.

Покупка ссылается на стабильный stockItemId единой inventory-позиции. GoodsPosted сохраняет deliveryId/lineId для происхождения движения и включает productId. Контракт задачи 1: stockItemId назначает STORE при первом приходе и возвращает в каталоге; в GoodsPosted его нет. Название и описание продукта передаются поставщиком и сохраняются в GoodsPosted.

### Порядок поставок и защита цены

Чтобы понятие «последняя» не зависело от задержек Kafka и разных часов, WAREHOUSE присваивает deliverySequence в пределах storeId при первом сохранении поставки. Значение монотонно растёт, присваивается один раз и не меняется при retry. Не требуется непрерывная нумерация без пропусков.

STORE хранит sequence последней применённой цены для inventory-позиции. Любая новая уникальная поставка добавляет количество, но обновляет цену только при более новом sequence. Поставка, которая ещё не получила цену, на каталог не влияет.

Пример: А(sequence=1) ждёт тариф; Б(sequence=2) уже оприходована по 144.00; затем А завершилась по 120.00. Количество от А зачисляется, текущая цена остаётся 144.00. Повтор события Б также не меняет количество или цену.

В поставке допускается одна строка на productId. Дубли продукта в одном payload отклоняются: иначе правило выбора цены внутри одной поставки становится неоднозначным.

### Корзина и цены

Корзина хранит ссылки на inventory и количества; её просмотр использует текущие цены STORE. Submit фиксирует цены и сумму из актуальных данных STORE внутри транзакции. Неподанная корзина не фиксирует цену. Уже принятая заявка сохраняет прежний snapshot в outbox, даже если пришла новая поставка.

### Поведение автоматического pricing

Фоновая задача выбирает наступившие WAITING_PRICING по nextAttemptAt. Ошибка TARIFFS/отсутствие подходящего правила сохраняет причину, количество попыток и следующую попытку. Временные ошибки используют ограниченный backoff; ожидающие поставки автоматически проверяются и после исправления правил.

Поставка с недопустимыми входными значениями получает REJECTED и автоматически не повторяется. HTTP выполняется вне длинной транзакции. Завершение pricing атомарно сохраняет POSTED и единственный outbox. Worker при рестарте восстанавливает сохранённые ожидания. Точная защита одновременных попыток определяется реализацией задачи 4 и проверяется integration-тестами.

## 3. Стратегия Git и PR

Remote default branch сейчас: master. Рабочая ветка при подготовке плана: codex/refactor-hardcoded-file-paths-in-myrunner; в ней есть изменение MyRunner.kt, не относящееся к этой переделке. Его не включать в архитектурные PR.

После подготовки плана документация перенесена в update-docs и смёржена пользователем в master через PR #36. Старая рабочая ветка удалена. Задача 1 начинается от master после этого merge; изменения исходников MyRunner к ней не относятся.

Задачи выполняются последовательно: ветка очередной задачи создаётся от обновлённой master после merge её зависимостей. Каждая получает один PR с кодом, собственными тестами и актуальной документацией. Пустые ветки и PR заранее не создаются. Merge и очистка данных не выполняются автоматически как часть подготовки плана.

Первый PR включает согласованные документы и контракты. Первоначальное ревью можно оставить как исторический документ с явной ссылкой на изменившиеся решения.

Собственные проверки: браузерные сценарии на реальном новом API; независимые корзины двух browser contexts; обновление цены; ошибка нехватки; потеря HTTP-ответа и reload с тем же ключом; отсутствие устаревших URL/авторизации; безопасное отображение названий/описаний товара.

Готовность: учебный путь доступен через существующий HTML без знания внутренней структуры API.

Оценка: 1–2 человеко-дня.

### Задача 8. Сквозные сценарии, отказоустойчивость и CI

Ветка: `codex/shop-e2e-ci`. Зависит от задачи 7.

Уточнено по ревью: Kotlin E2E запускаются на штатном Docker Compose без отдельного профиля и launcher. Удалены 12 сквозных сценариев с остановками контейнеров, управляемыми задержками и SQL-сбоем; интеграционные проверки модулей сохраняются. Текущий набор: 28 серверных запусков и 11 браузерных сценариев; конкурентные E2E и race удалены по следующему ревью. Результаты текущих тестов фиксируются после экспресс-ревью пользователя.

Результат:

- Перенести Kotlin E2E на новые контракты и изолированные fixtures; покрыть CASES-01–CASES-34.
- Дополнить уже существующие интеграционные проверки модулей-тесты сквозными проверками восстановлений, конкуренции, порядка поставок и цен.
- По последнему ревью не использовать отдельный профиль и управляемые точки отказа в E2E. Проверки восстановления остаются на уровне интеграционных тестов модулей.
- Подключить unit/integration и отдельный E2E stage к CI; сохранять отчёты и диагностику. Docker runner должен поддерживать Testcontainers.
- Завершить README: запуск из IDEA/Compose, миграции/fixtures, API, кейсы, ошибки, границы проекта. CASES содержит фактическое покрытие и ссылки на классы/методы.
- Очистить obsolete dependencies/config и настроить gitignore для build artifacts, не изменяя пользовательские исходники вне задачи.

Собственные проверки: полный reactor, интеграционные проверки всех сервисов, весь E2E набор и HTML smoke в чистой среде; реальный запуск CI workflow. Уже проверенные тесты не запускать многократно без новых изменений/неопределённости.

Готовность: все согласованные инварианты проверены, тесты не делят изменяемую корзину, документы совпадают с кодом, отчёты отражают реально выполненные проверки.

Оценка: 3–5 человеко-дней.

## 6. Оценка

Сумма задач: 18–28 человеко-дней. С резервом 20–30% — примерно 22–37 человеко-дней, около 4,5–7,5 рабочих недель для одного разработчика полной занятости. Человеко-день — 8 часов. Это предварительная экспертная оценка, а не обещание календарной даты.

По сравнению с первоначальными 16–25 днями добавлены сохраняемый автоматический pricing и защита цены от позднего завершения старой поставки. Подготовка текущих документов — часть первой задачи; её реальная оставшаяся длительность уточняется по мере работы.

Перевод backend на Kotlin, миграция исторических данных, промышленное масштабирование, платежи и новый frontend framework не включены.
