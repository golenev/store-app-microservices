# Слои backend

STORE, WAREHOUSE и TARIFFS организованы по техническим слоям. Корневые пакеты сохранены: `com.shop.store`, `com.shop.warehouse`, `com.tariffs`. В корне каждого находится только класс запуска Spring Boot. Сканирование компонентов охватывает подпакеты автоматически.

| Пакет | Ответственность |
| --- | --- |
| `controller` | HTTP-маршруты, параметры, статусы ответа и вызов сервисов |
| `service` | Бизнес-проверки, последовательность операций и транзакционные границы |
| `repository` | JDBC-запросы, отображение строк и блокировки; в TARIFFS также хранение снимков Redis |
| `dto` | Запросы и ответы HTTP; некоторые представления также используются при чтении сохранённых данных |
| `model` | Внутренние результаты разбора и захвата работ, состояние существующего остатка и правило тарифа |
| `messaging` | Kafka listeners и отправители; сетевые операции выполняются вне SQL-транзакций |
| `messaging.dto` | Конверты и содержимое Kafka-событий |
| `config` | Топики, повтор ошибок Kafka, часы, JSON и CORS |
| `exception` | Намеренные ошибки и безопасное преобразование в HTTP-ответ |
| `codec` | Строгий разбор, проверка и сериализация протоколов STORE/WAREHOUSE |
| `client` | Ограниченный по времени HTTP-клиент TARIFFS в WAREHOUSE |
| `validation` | Форматы строк публичного контракта TARIFFS |

Пакеты создаются только для существующих обязанностей. JPA и отдельного слоя `entity` нет: сервисы используют JDBC. Интерфейсы-пустышки и копии одной модели для каждого перехода между слоями не добавлены. Отдельный файл содержит один публичный тип; прежние контейнеры `ShopModels`, `DeliveryModels`, `TariffModels` удалены в пользу самостоятельных records.

## STORE

HTTP проходит через `ShopController` → `CartService` или `SubmissionService` → репозитории. `GoodsPostedListener` передаёт ключ, координаты и исходный JSON в `GoodsReceiptService`. SQL приёмки находится в `GoodsReceiptRepository`, общий доступ к остаткам — в `InventoryRepository`.

`SubmissionService` остаётся без собственной транзакции. `SubmissionTransactionService.accept` использует `REQUIRES_NEW`: блокирует корзину, затем остатки в порядке UUID, проверяет версию и количество, сохраняет submission, расходы, outbox и закрытие корзины атомарно. Конфликт UNIQUE сначала откатывается; `replay` читает победивший результат в новой транзакции. Репозиторий не открывает собственную транзакцию и не меняет этот порядок.

`StoreSender` захватывает сохранённое событие через сервис, публикует его после завершения SQL-транзакции и фиксирует результат по токену владельца. Повтор публикации сохраняет eventId и содержимое.

## WAREHOUSE

`DeliveryReceivedListener` → `DeliveryService` → `DeliveryRepository` сохраняет приёмку или диагностику до подтверждения Kafka. `DeliveryPricingService` получает захват, запрашивает тарифы через `TariffClient` вне SQL-транзакции и передаёт полный результат обратно в сервис. `post` атомарно сохраняет рассчитанные строки, POSTED и GoodsPosted outbox, проверяя токен под блокировкой.

`GoodsPostedPublisher` обслуживает исходящий outbox отдельно от расчёта. Обе фоновые задачи сохраняют прежнюю настройку `warehouse.workers.enabled`. Сроки захвата, частота опроса, топики и consumer groups сохранены.

HTTP учебного поставщика проходит через `DeliveryController` → `SupplierDeliveryService` → `DeliveryPublisher`. Проверка исходного содержимого предшествует отправке; ответ 202 требует подтверждения Kafka и не означает POSTED.

## TARIFFS

`TariffRuleController` вызывает `TariffRuleService` и `TariffQuoteService`. SQL находится в `TariffRuleRepository`, Lua и Redis — в `TariffQuoteCache` пакета `repository`. `QuoteCacheLookup` хранит результат чтения и поколение сброса отдельно от реализации кеша.

CRUD сохраняет прежние транзакции и версии правил, не сбрасывает заполненный кеш. Расчёт и Redis не оборачиваются в общую SQL-транзакцию. Недоступный Redis допускает расчёт по PostgreSQL; сброс требует реального успеха Redis.

## Проверки

```shell
python scripts/check-backend-layers.py
mvn clean verify
```

Проверка структуры включена в CI. Она проверяет пути пакетов, отдельные публичные типы, явные импорты между слоями, отсутствие прямого JDBC/Redis вне репозиториев и Kafka вне конфигурации/обработчиков сообщений. Это проверка исходников, а не анализ всех зависимостей байткода или динамических обращений.

Сервисные API↔PostgreSQL тесты используют настоящие сервисы и репозитории с production Flyway в отдельных Testcontainers. Изменение Java-пакетов не требует изменения внешних HTTP/Kafka-контрактов, SQL-миграций, HTML или Kotlin E2E. Полный E2E проверяется отдельно; успех Maven не заменяет его.

Локальная проверка 10 октября 2026: `mvn clean verify` на Java 21 — 133/133 без ошибок и пропусков, включая 35 API↔PostgreSQL сценариев и 62 проверки контрактов. Проверка структуры проходит для 81 production Java-файла. Дополнительно сопоставлены SQL-запросы, поля прежних records и транзакционные аннотации с базовой `master`: различий в контрактах и границах транзакций нет. Kotlin E2E в этой задаче не запускался.
